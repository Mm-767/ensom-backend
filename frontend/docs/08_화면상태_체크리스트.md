## 0. 왜 이 문서가 따로 필요한가

`03_화면설계서.md`는 "화면"(사용자가 도달하는 장소) 단위로 정리되어 있고 상태는 각 화면 설명 안에 산발적으로 있었다. 실제 개발 티켓을 끊으려면 **상태 하나하나가 "만들어야 할 화면 하나"**이기 때문에 (로딩 스피너도, 빈 상태 문구도, 확인 모달도 전부 디자인·코드가 필요하다) 화면 44개를 상태까지 곱하면 실제 작업 단위는 그보다 훨씬 많다. 이 문서는 그 곱집합을 빠짐없이 세는 게 목적이다.

**새 화면 ID는 만들지 않는다** — 상태는 소속 화면의 상태로 문서화한다(예: "일정 없음"은 `HM-01`의 상태이지 새 ID가 아니다). 단, 지금까지 **어느 화면에도 속하지 않고 완전히 빠져 있던 것**은 §4에서 신규 ID를 부여한다.

## 1. 공통 상태 7종 정의

모든 화면에 기계적으로 다 만들 필요는 없다 — 아래 정의를 기준으로 화면별로 "해당됨/안됨"만 표시한다(§3 매트릭스).

| 코드 | 상태 | 정의 | 사용자 행동 기본값 |
|---|---|---|---|
| **L** 로딩 | 데이터를 서버·외부API에서 받아오는 중 | 스켈레톤 또는 스피너. 5초(계획)·2초(WIS) 넘으면 안 됨(PRD §23.1) | 없음(대기), 취소 가능하면 취소 |
| **E** 빈 상태 | 정상 응답인데 데이터가 0건 | 사과 문구 금지, 다음 행동 유도 CTA 최소 1개 | CTA 탭 → 데이터 생성 화면 |
| **X** 에러 | API 실패·네트워크 문제·부분 실패 | 마지막 성공 데이터 유지 + 기준 시각 표기, 반복 노출 금지(PRD §23.2) | 다시 시도, 또는 그냥 둘러보기 |
| **S** 성공/완료 | 사용자 액션이 서버에 반영됨 | 토스트(2~3초 자동 소멸) 또는 다음 화면으로 즉시 이동 자체가 성공 신호 | 없음(자동 진행) 또는 [되돌리기] |
| **P** 권한요청 | OS 권한이 필요한 기능 진입 | 프라이밍 화면(왜 필요한지) → OS 네이티브 다이얼로그. 거부 후 재요청은 기능 진입점에서 1회만(PRD §11.4) | 허용 / 나중에(거부) |
| **C** 확인모달 | 되돌리기 어렵거나 데이터에 영향 있는 행동 | 바텀시트 또는 중앙 다이얼로그, 취소 기본 강조 | 확인 / 취소 |
| **V** 검증오류 | 폼 입력값이 유효하지 않음 | 필드 인라인 오류 문구, 제출 버튼 비활성 또는 제출 시 차단 | 값 수정 후 재제출 |
