## 2. 화면 구현 현황

신규 명세의 화면/상태 ID 약 46개 중 실제 라우트와 동작이 확인된 화면은 약 18~20개다. 단순 파일 존재가 아니라 진입 경로와 API 동작을 함께 기준으로 산정했다.

### 구현 또는 부분 구현

- S-01 로그인(이메일/Google), S-01E 오류 일부
- S-02 약관 동의
- S-03 준비 시간·준비 항목
- S-04 주요 장소
- S-05 웰니스
- S-06 홈, S-07 알림 로그
- S-08 지도 기본 일부, S-10 일정 생성, S-12 일정 상세
- S-14 프로필 및 권한/알림/개인화/데이터 일부
- S-16 이메일 가입(현재 BE 필드 범위), S-17 링크 기반 이메일 인증 안내
- S-34 권한 프라이밍 UI, S-37 스플래시, S-39/S-40/S-43 공용 시트
- S-41 캘린더 OAuth 연결·해제
- S-42 온보딩 완료

### 누락·placeholder·도달 불가

- S-18 가입 완료
- S-19/S-20 비밀번호 찾기·재설정
- S-21/S-22/S-23 약관 본문·개인정보·고객지원(실제 문서/정책 URL 필요)
- S-24~S-29 계정 상세(비밀번호/이메일/로그인 수단/2FA/로그인 기록)
- S-30/S-31 북마크 목록·편집, S-32 빠른 선택
- S-13 일일 마무리 진입, S-15 주간 리포트 API
- S-44 사후 평가의 조건부 노출
- 온보딩 완료 여부를 서버 값으로 판별해 중간 단계로 복귀하는 라우터 상태

## 3. BE 계약 대조

### 현재 연동 가능

| 기능 | BE 계약 |
|---|---|
| 이메일 가입/로그인 | `POST /auth/email/signup`, `POST /auth/email/login`; 가입 DTO는 `email`, `password`만 수신 |
| Google 로그인 | `POST /auth/google` |
| 이메일 인증 | `POST/GET /auth/email/verify`, `POST /auth/email/verify/resend`; 6자리 OTP가 아니라 이메일 링크 token 방식 |
| 약관 | `POST /consents` |
| 권한 | `GET/PATCH /me/permissions` |
| 캘린더 OAuth | `POST /calendar/google/connect { authCode }`, `DELETE /calendar/google` |
| 회원 탈퇴 | `DELETE /me` |

### BE 선행 필요

| 명세 기능 | 현재 충돌/부재 |
|---|---|
| S-16 이름·닉네임·중복확인 | Signup DTO 필드와 중복확인 endpoint 없음 |
| S-17 6자리 인증 | BE는 링크 token 방식. 제품/BE 결정 전 OTP UI 구현 금지 |
| S-19/S-20/S-25 비밀번호 reset/change | endpoint 없음 |
| S-26 이메일 변경 | endpoint 없음 |
| S-27 로그인 수단 관리 | 조회·연결·해제 endpoint 없음 |
| S-28 2FA | 엔티티·endpoint 없음 |
| S-29 로그인 기록 | 기기별 세션 조회·해제 endpoint 없음 |
| S-30/S-31 북마크 | 엔티티·endpoint 없음 |
| S-14E 행동 기록 삭제 | endpoint 없음. 개인화 초기화와 다른 기능 |
| S-15 주간 리포트 | 명세에서도 endpoint 미정(P1) |

## 4. 구현 원칙과 후속 순서

1. BE 없는 기능은 성공한 것처럼 보이는 stub API나 가짜 로컬 데이터로 연결하지 않는다.
2. 정적 정책 화면은 실제 약관 본문·개인정보 URL·고객지원 채널이 확정된 뒤 연결한다.
3. 이메일 인증 방식은 **현재 BE 링크 방식 유지** 또는 **BE OTP 전환** 중 제품 결정을 먼저 한다.
4. 다음 FE 우선순위는 서버 계약이 필요한 온보딩 완료 상태 복귀와 계정·북마크 기능이다.
5. 계정·북마크·비밀번호 기능은 BE 계약 이슈와 함께 별도 PR로 구현한다.
